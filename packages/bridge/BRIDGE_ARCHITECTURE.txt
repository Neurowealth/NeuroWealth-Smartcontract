NeuroWealth Cross-Chain Bridge Architecture
Phase 3: Stellar ↔ Ethereum via Axelar
================================================================================

OVERVIEW
--------
The bridge enables seamless cross-chain transfer of USDC between Stellar and
Ethereum using Axelar's General Message Passing (GMP) protocol.

Flow: User (Ethereum) → Axelar → Vault (Stellar)

SUPPORTED FLOWS
---------------

1. ETHEREUM → STELLAR (Deposit)
   1. User initiates deposit on Ethereum dApp (via eth-bridge-connector)
   2. USDC transferred to bridge contract on Ethereum
   3. Bridge emits event with destination Stellar address
   4. Axelar relayers pick up event and sign it
   5. Axelar GMP message submitted to Stellar
   6. Vault contract receives GMP message verification
   7. User receives USDC in Stellar vault (minus bridge fee)

2. STELLAR → ETHEREUM (Withdraw)
   1. User initiates withdrawal via vault UI
   2. Vault contract holds shares for burning
   3. Vault contract sends withdrawal request to bridge
   4. Bridge verifies Stellar transaction
   5. Axelar relayers bridge USDC to Ethereum
   6. User receives USDC on Ethereum (minus bridge fee)

KEY COMPONENTS
--------------

BridgeManager
  - Orchestrates transfer initiation (Stellar/Ethereum)
  - Executes via Axelar GMP
  - Polls transfer status
  - Handles retries and timeouts
  - Validates amounts against min/max
  - Writes every transition through to the store, so a restart resumes from
    durable state instead of process memory (#848)
  - loadDurableState() rebuilds the in-memory view from the store at startup

BridgeStore
  - Persistent storage for bridge transfers
  - In-memory (development) or SQL/PostgreSQL (production)
  - Tracks: ID, status, addresses, amounts, hashes, retries
  - Durable workflow state: stage, attempt count, sanitised last error,
    next-attempt deadline and last reconciliation time (#848)
  - Writes are atomic: a record is either fully updated or left untouched

TransferReconciler
  - Startup pass over every durable non-terminal record (#850)
  - Queries BOTH chains before deciding, so a transfer the destination already
    executed is adopted rather than resubmitted
  - Actions: skipped_terminal, resumed, confirmed, failed, awaiting_external,
    backoff
  - Unknown external states stay retryable behind a bounded exponential
    backoff (30s base, 15m cap) instead of hot-looping
  - Returns a summary with counts by action, terminal state and error class

BridgeMonitor
  - Continuous monitoring of pending transfers
  - Auto-retry failed transfers (up to 3x)
  - Timeout detection (30 minutes)
  - Health metrics (confirmation time, failure rate)

SECURITY MODEL
--------------

Key Assumptions:
  ✓ Axelar network is trusted (uses threshold signatures)
  ✓ Ethereum smart contracts are audited
  ✓ Stellar vault is non-custodial (users hold private keys)
  ✓ All bridge operations are transparent and auditable

Protections:
  1. Amount Validation
     - Min bridge amount: $100 USDC
     - Max bridge amount: $100,000 USDC
     - Prevents dust transfers and caps exposure

  2. Fee Collection
     - 0.5% bridge fee (configurable)
     - Covers Axelar relayer costs + platform fee
     - Users see exact netAmount before confirmation

  3. Timeout Handling
     - 30-minute timeout on pending transfers
     - Auto-fails if no confirmation
     - Funds can be manually recovered via cancel_bridge

  4. Signature Verification
     - Axelar relayer signatures verified via ECDSA
     - Invalid signatures rejected
     - Prevents relay attacks

  5. Audit Trail
     - All transfers logged to bridge_audit_log
     - Event types: initiated, submitted, confirmed, failed
     - Queryable for compliance/forensics

  6. Rate Limiting
     - Per-user rate limits (optional)
     - Per-bridge limits to prevent congestion
     - Protects against spam/griefing

FAILURE MODES & RECOVERY
------------------------

Scenario 1: Bridge transfer stuck in "pending"
  Cause: Source chain transaction not picked up by relayers
  Action: Manual retry after 1 hour
  Prevention: Monitor bridge_transfers table, alert after 5 min

Scenario 2: Axelar relayer failed to sign
  Cause: Axelar network congestion or temporary outage
  Action: Automatic retry (up to 3x) with exponential backoff
  Prevention: Use multiple Axelar validators, geographic diversity

Scenario 3: Destination chain rejection
  Cause: Contract upgrade, governance change, or attacked contract
  Action: Manual investigation, potential fund recovery
  Prevention: Governance approval before major changes, circuit breaker

Scenario 4: Incorrect amount delivered
  Cause: Precision loss or slippage calculation error
  Action: Manual audit via Axelarscan, recovery transaction
  Prevention: Comprehensive testing on testnet, staged rollout

MONITORING & ALERTS
-------------------

Critical Alerts:
  - Transfer timeout (30 min elapsed, still pending)
  - Relayer signature verification failed
  - Destination amount mismatch
  - Repeated retries exceeding 3 attempts

Warning Alerts:
  - High failure rate (>10% in past hour)
  - Unusual bridge volume spike
  - Axelar network latency (>15 min confirmation)

Metrics to Track:
  - Average confirmation time (target: <10 min)
  - Success rate (target: >99%)
  - Bridge volume (daily, hourly)
  - Fee revenue (USD equivalent)
  - Failed transfers (cumulative)

AXELAR INTEGRATION DETAILS
---------------------------

GMP Message Flow:
  1. Source Chain: User → Bridge Contract (transfer + message)
  2. Axelar Hub: Collect signatures from validator set
  3. Destination Chain: Execute with >= 2/3 weighted signatures
  4. Vault: Process GMP, mint/burn shares

Payload Format (hex-encoded JSON):
  {
    "version": 1,
    "transferId": "uuid",
    "user": "G... or 0x...",
    "amount": "50000000000",
    "destinationChain": "stellar",
    "timestamp": 1234567890
  }

Gas Estimation:
  - Ethereum: ~300,000 gas (deposit) + relayer fee
  - Stellar: ~100,000 stroops (confirmation)
  - Axelar: Baked into bridge fee (0.5%)
